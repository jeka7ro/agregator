Versioning
Versioning and Backward Compatibility Policy

The Bolt Delivery API is a rolling-version API. The structure of API requests and responses is maintained as fully backward compatible with the very first API version ever released. In practice, this means the following:

In the request formats to the API (i.e., the part the integrator needs to implement):
No existing endpoints are ever removed, but new ones might be exposed.
No mandatory fields can be introduced, but new optional fields might appear.
Existing mandatory fields could become optional or deprecated (the latter implying their usage is not recommended but will be supported).
In the response formats, including webhook payloads (i.e., the data the integrator receives from Bolt):
No mandatory fields are ever removed, but new ones might be exposed.
Existing optional fields could become mandatory or deprecated (the latter implying their usage is not recommended but will be supported).

Overall, Bolt makes every reasonable effort to ensure the business logic remains operational and that no changes need to be implemented when newer versions of the API are released.

Authentication
Integrator webhooks authentication

For authenticating requests coming from Bolt Food there are two options:

Basic authentication
Utilizing an identity server
Basic authentication
You will provide us with a username and a password and we will send an Authorization header with each request to your endpoints.
The Authorization header that we will send will have the value: Basic base64($username:$password)
Identity server for getting a bearer token

This will imply that you will give us an endpoint that we will call with a payload you can specify (e.g. client_id, client_secret, scope, etc.). The payload will be encoded as x-www-form-urlencoded in a POST request to your identity server.

The response from this endpoint will contain 2 things:

token - this will be a token that we will then use in the Authorization header for subsequent requests to your endpoints (webhooks);
expires_at - timestamp at which the token will expire, we use it to cache the token so we don’t send requests to your identity server each time we need to call one of your webhooks. The format that must by used is the unix timestamp in seconds
Signing request that reach Bolt Food API

In order to secure the communication, we will verify the signature for all the requests that are reaching our API. We will require 2 headers with each request we get on our webhooks:

x-external-integrator-id which contains your integrator id (you will get this from Bolt Food when your test account will be created);
x-server-authorization-hmac-sha256 which contains the signature of the raw payload (outputed in base64) computed with sha256 algorithm and a secret key that you will receive from Bolt Food. Example how to compute it can be found in the Postman collection or following this code snippet example:
const CryptoJS = require('crypto-js');
const secret = '<put your secret key here>';
const body = pm.request.body.raw;
const key = CryptoJS.HmacSHA256(body, secret);
const base64key = key.toString(CryptoJS.enc.Base64);
pm.request.headers.upsert({
    key: 'x-server-authorization-hmac-sha256',
    value: base64key
});

API changes and request handling
Idempotency rules for Bolt outbound traffic

Due to retry mechanism Bolt might send the same event multiple times. To prevent issues with order duplication integration system must assure idempotency. For example when receiving the same order_id for event:

new_order : Integrator should send back HTTP 200 response for each request and make sure to not duplicate the order
cancel_order: Order should be canceled and HTTP 200 response have to be sent to each request
Outbound request retries

Bolt Food provides functionality to retry an outbound request in order to increase the probability of receiving a successful response.
This functionality is disabled by default and can be enabled by contacting Bolt Food support.

When are outbound requests retried?

An outbound request will be retried from Bolt’s side for one of the following scenarios:

The received response was not successful (HTTP 2xx response code)
The request timed out

The timeout for an outbound request is 5 seconds.

How often are outbound requests resent?

Bolt Food will retry sending outbound requests until a successful response is received or after a total of 5 retried attempts is reached.

The attempts are resent using an exponential backoff algorithm by resending after 2request_attempt_number seconds, where request_attempt_number is in the range [1…5].

This means that the requests will be sent using the following time frame:

First retry: at least 2 seconds after the original request was rejected.
Second retry: at least 4 seconds after the previous request was rejected.
Third retry: at least 8 seconds after the previous request was rejected.
Fourth retry: at least 16 seconds after the previous request was rejected.
Fifth retry: at least 32 seconds after the previous request was rejected.

Menu integration
Menu structure

ℹ️ Each provider can have only one active menu.

Bolt Food menu has the following components:

Category - Consists of one or more dishes (assigned in children_ids). E.g. Breakfast, Burgers, Lunch etc.
Dish - Item inside a category. It may have none to many option groups assigned (children_ids)
Option group - Group which can be assigned one to many dishes. E.g. "Selecti your pasta type", "Add extras to your pizza"
Option - options inside option groups. E.g. "Short pasta", "Extra cheese"
Tags - predefined list of tags to mark item e.g. as packaging_fee, vegeterian etc.
Fees - Item defining a fee, such as bottle deposits, SUP directive fees, which can be assigned to other items of type Dish or Option.
(Deprecated - please do not use) Tag multipliers - Array used in order to denote how many tag instances are attached to a single item. Example: [{tag: “sup_cup”, multiplier: 3}, {tag: “sup_container”, multiplier: 2}]. Currently only used for SUP directive business tags.

Item availability

Each menu push (/pushMenu) will overwrite previous menu and item availabilities, meaning all unavailable items should be sent to /updateMenuItemAvailability after every menu push with one request (all unavailable items combined into one request). Afterwards dishes and/or options can be updated with /updateMenuItemAvailability.

Fees

Menu items of type "fee" are used to define the applicable fees for items in the menu being pushed, as defined by various container-deposit legislations across markets. The price of a fee is applied on top of the base price of the menu item for which the fee is assigned. For example if a menu item is priced at 10 EUR, and has a fee assigned, with the price of the fee item being 0.5 EUR, then the total price amount of the item will be 10.5 EUR. The extra price from the attached fee is reflected accordingly in the Bolt Food application. By default, for the currently supported fees, the fee price is not included in the merchant's commission computation, the applied VAT rate for the fee price is 0 and the fee price is not included in any discount computation. Currently the following fee types are supported:

Provider integration
Overview

In Bolt Food's ecosystem, providers operate under two statuses: active and inactive. While both statuses allow providers to be visible in the app, the inactive status prevents customers from placing orders. Providers are automatically closed based on their designated working hours.

Managing Provider Statuses

The provider status, whether active or inactive, serves to temporarily pause receiving new orders. This status can be modified using two key actions:

pauseOrders This action transitions the provider to an inactive state, halting order reception.
startAcceptingOrders This action reactivates the provider, allowing them to resume receiving orders.

Additionally, a Status Update Webhook is triggered each time the provider's status changes. These changes can occur due to actions initiated by the integrator, by Bolt Food when a provider misses an order, or through manual adjustments made within the Bolt Food backoffice.

Dine-In Order integration
Introduction

The Dine-in initiative introduces a new experience by allowing customers to use QR codes on restaurant tables to place orders and pay through the Bolt Food ecosystem.

Terminology

Order & Pay (O&P): Upon arriving at a restaurant and being seated at their table, diners can scan a QR code provided on the table. This QR code directs them to an easy-to-use interface where they can browse the menu, add items to a basket, review their selection, and proceed to checkout to pay for their order. Once the payment is successfully completed, the order will be sent to the restaurant for preparation and served to the diners.
Note: No additional items can be added to the order after the payment is completed. If diners wish to order more, they will need to place a new order.

Pay & Go (P&G): Upon arriving at a restaurant and being seated at their table, diners wait for the waiter to take their order. Once the order is placed by the waiter through the POS system, diners can scan a QR code available on their table. This QR code directs them to an interface where they can view the details of their placed order. From this interface, diners can proceed to checkout and pay for their order conveniently through the Bolt platform.

Receiving dine-in orders

The dine-in orders will be received through the same partner webhook that you are currently using: New Order

The main difference between the Regular order is dine-in orders are the following:

In order to differentiate the dine-in order from other order types (“delivery”, “pickup”, “own_delivery”) you can use a new value that will be added to the order_type field: “dine_in”
In order to use dine-in orders, you’ll have to use a new field instead of order_id which will be called extended_order_id: string.

ℹ️Please note that for this dine-in case you’ll have to follow Idempotency rules for outbound traffic for extended_order_id instead of order_id, since the order_id can be duplicated for the Pay & Go scenario.

ℹ️The extended_order_id will have the following format “${main_order_id}_${item_group_id}” (which are presented more bellow, although you can consider the format nonessential)

The specific dine-in information will be in a present in a dine_in_details object that consists of the following fields:
table: string => this will contain the table number in a string format
item_group_id: number => present in the composition of the extended_order_id, can be considered nonessential and was added for potential future enhancements and overall flexibility
main_order_id: number => present in the composition of the extended_order_id, can be considered nonessential and was added for potential future enhancements and overall flexibility
waiter_tip: GenericPosPrice => the tips the waiter has received for the order

Pay & Go (P&G)
Order flow for integration:

Order Placement: The waiter takes the customer's order and enters it in the POS system.

Viewing Orders: Customers can scan the QR code on their table at any time to view active orders for that table. Additionally, they can check detailed order information on the checkout screen. Order data is fetched from the POS system through a Get Active POS Orders for Table outbound request, ensuring it reflects the most up-to-date order details.

Paying for the Order:

Locking the Order: When the customer opts to pay, the order is locked to prevent further modifications. This is achieved by sending a lock update request (is_locked = true) to the POS system.

Order Creation on Bolt: After the order is locked on the POS system, a corresponding order is created on the Bolt platform, allowing the customer to proceed with payment.

Handling Unfinished Payments: If payment is not completed within a specified time frame, the lock on the POS order is automatically released through an outbound lock update request (is_locked = false). The order can be now modified on the POS side, if needed.

Finalizing the Order: After the payment is successfully completed on Bolt, an outbound Order Update request with the type order_paid is sent, confirming the order's completion.

2. Update Order Lock

This request locks an order for payment, preventing any further modifications. It updates the is_locked status of the specified order and returns the updated order details. Locking the order ensures that no changes can be made during the payment process, preserving the integrity of the payment amount and order details. If the payment is not completed within a configurable time frame, the system will automatically send this outbound request again to unlock the order, allowing the eater to modify it before attempting payment again. This process ensures a seamless and consistent payment experience while maintaining accurate order information.

Request Body:

Parameter	Type	Required	Description
external_order_id	string	Yes	Unique order identifier provided by POS for the order.
provider_id	string	Yes	Unique identifier for the POS provider.
is_locked	boolean	Yes	Specifies whether acquire (true) or release (false) POS order lock.

3. Payment notifications
3.1 Order Paid Notification

After the order is paid, a Receive Order Update outbound request of ORDER_PAID type is sent. This includes external_order_id which is the order identifier provided by POS.

3.2 Order Paid Partially Notification - Split Bill

For cases where diners wish to split the bill, a partial payment can be made for selected items. Once the payment is completed, an outbound Receive Order Update request of type ORDER_PAID_PARTIALLY is sent. This request includes the external_order_id (the order identifier provided by the POS system), the order_items_total for the selected items, and a list of the selected order_items.

When Get Active POS Orders for Table is being later called, the paid items should no longer appear in the active order, once the POS system processes the request.

Note: Any other webhook outbound requests that are not mentioned as part of Pay&Go flow should be ignored for Pay&Go orders.

required

The type of update request received. Used to mark events and differentiate between payloads.

PIM integration: Option and Option Groups
Create or Update Options
POST
/pim/v1/option/upsert

Creates options in bulk or updates options attributes if they already exist (identified by SKU). (you can enable this feature by contacting the Bolt Food support) sku attribute is optional for creating options, if not provided, the option will be created with a generated SKU. sku attribute is mandatory for updating options.

extended_sku attribute is the SKU of the product/dish the option is meant to extend and inherit its attributes (tags, codes and prices) if not overridden. extended_sku is optional and can be updated later. If not product found with provided extended_sku, a PRODUCT_NOT_FOUND (code: 40018) error will be returned and changes will be discarded.

HEADER PARAMETERS
x-external-integrator-id
required
string

Integration ID provided by Bolt Food. It will be unique across all providers.

required
string
